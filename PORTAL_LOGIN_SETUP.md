# Portal email/password login

The portal now uses company-created email/password accounts stored in Cloudflare D1. No email service, ChatGPT Sites identity headers, authentication API key, or public registration is required. Existing project and file authorization still uses the signed-in email; owner access still uses the allowlist in `lib/auth.ts`.

## Deploy

Publish these repository changes to GitHub and let Cloudflare rebuild. Keep the existing build command that replaces the generated D1 placeholder with `bfe4fcc7-f61c-4a30-8cae-2d936347b5ea`; `pnpm build` alone still emits the local-development placeholder. Keep the deploy command:

```sh
pnpm exec wrangler deploy --config dist/server/wrangler.json
```

Before using sign-in, open Cloudflare → D1 → your production database → Console, and execute the contents of `drizzle/0001_password_auth.sql` **once**. This creates only the new authentication tables/indexes and preserves existing projects and website content. If you use a migration runner, apply this migration through that runner instead; do not apply it twice. The `site_content` table from `0000_omniscient_gladiator.sql` must already exist.

## Let clients choose their own password

Apply `drizzle/0002_client_invitations.sql` once in the production D1 Console after the authentication migration above. Deploy the updated app.

In `/admin`, add the client's project and sign-in email, then click **Save client dashboard**. In that client's card, click **Create password setup link**, then **Copy link**. Send the link privately to that client through your established communication channel. The client opens it, chooses and confirms a password of at least 16 characters, then signs in at `/portal` with the email assigned to their project. No company-chosen password or email provider is needed.

Links expire after 24 hours and work once. Generating a replacement invalidates the previous link. Treat links as credentials: anyone holding an unused link can set that client's password. Only hashed tokens are stored in D1; the token is carried in the URL fragment rather than query parameters so it is not sent in server request URLs. Reopening the editor does not retrieve old links; generate a new one if needed.

Clients with existing passwords keep their accounts and cannot be reset using an onboarding invitation. The company can reset an existing password through the trusted account tool below. There is no public registration or automated invitation email. Removing a project prevents its pending setup link from being redeemed unless another saved project still assigns that email.

## Password resets and changes

Apply `drizzle/0003_invitation_kind.sql` once in the production D1 Console (after `0002`). It adds the `kind` column that separates first-time setup links from reset links, and the `auth_email_codes` table for password-change codes.

Everything a client starts themselves is verified through their inbox. Owner-issued links from `/admin` don't need email verification.

- **Forgot password (self-service):** `/signin` links to `/forgot-password`. A client enters their email and receives a one-use link valid for 24 hours. It sets a first password for a saved client without an account, or resets an existing account and signs out its sessions. Unknown emails get the same response. Requests are limited to 3 per email and 10 per IP per hour. This needs the Google Workspace mail secrets (`GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_SERVICE_ACCOUNT_KEY`, optional `GMAIL_SENDER`); until they're set, the page says reset by email isn't available.
- **Owner-issued links:** in `/admin`, each client card can **Email password link to client** (needs mail secrets) or **Create link to copy**. Clients who already have an account get a reset link instead of an error.
- **Change password:** signed-in users open `/change-password` from the portal header. It requires the current password **and** a 6-digit code emailed to the account (valid 10 minutes, 5 tries per code, 5 codes per hour). It signs out every other session. Without the mail secrets, password changes are unavailable and clients are told to contact their project manager.

A setup link can only create an account and a reset link can only change an existing one, so a setup link issued before an account existed still can't overwrite its password.

## Create the owner account or reset an existing password

On a trusted computer with Node.js, run from the repository:

```sh
node scripts/create-portal-account.mjs client@example.com
```

The tool asks for a hidden password and confirmation. Use a unique password of at least 16 characters, preferably generated by a password manager. Do not pass passwords as command-line arguments, paste them into chat, or commit them. The tool creates a private SQL file containing only the normalized email, random salt and derived password hash, then prints its path.

Open that SQL file locally and execute its contents in the same production D1 Console. For an existing email this resets the password and revokes all its sessions. Treat the hash file as confidential and delete it after applying it. Share the password with the client through your established secure channel.

Create the owner account using the exact owner email already in `lib/auth.ts`. Then visit `/admin` to assign projects to each client's sign-in email. Clients sign in at `/portal` and see only projects/files assigned to that email. An account with no assigned projects shows an empty dashboard.

There is no automatic forgotten-password email. Reset through the same trusted account tool. To disable an account, delete its row from `auth_users` and its rows from `auth_sessions` in D1, filtering by the exact normalized email.

## Security and sessions

Passwords use individually salted PBKDF2-SHA256 with 100,000 iterations (the Workers Web Crypto limit) and a 16-character provisioning minimum. Sessions expire after seven days and only token hashes are stored. The host-only cookie is HttpOnly, Secure and SameSite=Lax; production must use HTTPS. Sign-out uses a same-origin POST, deletes the server session, and clears the cookie. Login checks the request origin, bounds request bodies, returns generic invalid-credential errors, and throttles by email and IP. Ten login attempts per email and thirty per IP are permitted per fixed 15-minute window, including successful attempts. Configure Cloudflare edge rate limiting as needed for larger deployments.

Caller-provided `oai-authenticated-user-*` headers no longer grant access. Legacy sign-in links redirect to the password form. The account SQL tool never connects to production itself.

## Validate locally

```sh
pnpm build
node --experimental-strip-types --test tests/password-auth.test.mjs tests/client-invitations.test.mjs
node tests/password-auth.integration.mjs
```

Tests use Node 24 (the invitation test uses native TypeScript resolution hooks). The integration test starts a local Worker with disposable D1/R2 state and synthetic accounts/projects; it never uses production resources. It retries once only when Wrangler explicitly reports that its development proxy restarted mid-request; application failures are not retried. It checks login, access isolation, rejected identity spoofing, sign-out, and cookie protections. Existing repository-wide type and lint failures in the editor, portal dashboard, sidebar and project validator remain outside this change.
